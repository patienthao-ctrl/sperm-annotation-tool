# 0004 多人协作：文件夹、批量导入导出与分工

- 日期：2026-11-04
- 状态：采用，阶段 0 和 1a–1c 已实现（现行规则见 WORKFLOW、API）

> 要点
> - 定位：这是内部小团队做训练数据集的工具，不是商业软件。只解决真正卡人的问题，不加新页面，尽量不加新操作。
> - 先修一个已实测的审查漏洞和几个批量时必然失败的问题。
> - 文件夹就是每段视频多记一个路径，按导入时的目录自动生成，视频文件不移动。
> - 导出按钮还在原处，弹窗里可以多选。
> - 不做任务分配、角色和权限：谁在做什么从现有记录自动显示，分工靠文件夹和日常沟通。
> - 审查通过永远逐段逐帧，不做批量通过。

## 背景

工具已经能多人同时编辑一段视频（[0001](0001-多人协作工作区合并.md)），但一批视频的导入、查找和导出都要一段一段来。

“依据”一列：**实测**是 2026-11-04 在隔离目录用合成数据跑过；**读代码**是从代码和配置确认，未跑真实流程。

| 问题 | 现状 | 依据 |
| --- | --- | --- |
| 不能按文件夹导入 | 视频只能在同一目录里多选；标注包一次只能选一个 | 读代码 |
| 视频没有分类 | 所有人的视频在一个平铺列表里，只能按文件名搜 | 读代码 |
| 不能批量导出 | “一起导出”只列出逐段导出过的视频，所以要先逐段打开导出一次；也查不出“我审查通过的” | 读代码 |
| **审查通过可能包含没人看过的改动** | 确认某帧只记“谁、何时”，不记当时的内容。审查员确认第 1 帧后同事再改这一帧，它仍算已确认，审查照样通过，记录还写着由原审查员确认，之后也能进训练集。重新追踪走同一条路（这部分读代码） | 实测 |
| 批量导出慢到不可用 | 打包时每 20 帧、查进度时约每秒，都重读包内全部视频的标注。100 段 × 3000 帧单次约 14 秒（不含打开视频），只算打包这一项至少多 59 小时；阶段 0 后单次约 1.3 毫秒，累计约 20 秒 | 校验开销实测，总量按代码换算 |
| 固定快照会和别人的保存冲突 | 拿不到全局锁就直接报“正在保存”；拿到后持锁算整个视频的 SHA-256，别人的保存都要等 | 读代码 |
| 大包下载不下来 | 整包要先完整读进浏览器才保存，5 分钟超时；100 Mbps 内网约 3.7 GB 就会超时 | 读代码，按带宽换算 |
| 超过 2 GiB 的标注包传不上去 | 后端允许 8 GiB，Docker 里的 nginx 只放行 2 GiB | 读配置 |
| 一个文件失败，后面全不导入 | 循环遇错退出，不报告哪些成功；每个重复视频弹一次窗，卡住队列 | 读代码 |
| 上传没有进度，素材库全程锁住 | 导入期间不能切换视频 | 读代码 |
| 误删找不回 | 删除和覆盖重标都直接清掉文件，已通过审查的视频也一样 | 读代码 |
| 状态和人看不清 | 没动过的视频也显示“待审查”；审查提示写“用户 #3”；同事导入或通过后要刷新页面才看到 | 读代码 |

实测**不是**问题、不用优化的：状态汇总 `/annotation-review/summary`，300 段、每段 3000 帧 5 框约 0.2 秒。

## 决定

### 1. 先修的问题

这些都不增加新操作：

- **审查确认绑定内容**：确认时记下这一帧内容的摘要；内容变了就自动退回未确认，并提示第几帧被改动和最后保存的人，通过时再核对一次。升级前已有的确认没有摘要，按有效处理。实现时发现同类问题也一并修了：重新审查进行中，清单外的帧被改动时自动计入本轮。
- **导出减负**：打包时只比较文件标记，变了才完整校验；查进度时不校验；生成结束和下载前仍完整校验，失效规则不变。
- **固定快照**：不再持锁算哈希（用 `media_reimport.source_sha` 的指纹缓存，打包时仍校验真实 SHA），遇到别人保存时等一下而不是报错，内容没变就复用已有快照。
- **大文件**：nginx 上限改为和后端一致的 8 GiB；下载改用浏览器原生下载，直接存盘，没有 5 分钟限制。JPG 不再压缩，打包更快。
- **误删可找回**：删除和覆盖重标改为把文件移进 `_trash/`（现有扫描已跳过 `_` 开头的目录）。不做界面，需要时手动移回，也手动清理。
- **显示**：状态按第 4 节推导，审查提示显示用户名。

### 2. 文件夹

- 每段视频多记一个路径，如 `2026-10 第一批/样本A`。树由路径算出来，没有单独的文件夹表，文件夹空了自然消失。视频文件留在原处。
- 路径来自导入时选的目录；标注包用包名。现有视频没有路径，显示在“未分类”。系统不看视频内容自动分类。
- 素材库抽屉改成文件夹树，每行显示段数和各状态数，展开和收起记在本机。可以按状态筛选，也可以勾选“我审查的”。
- 抽屉里加一个“整理”窗口：勾选视频，输入或选择路径即可移动；也能重命名文件夹。不做单独的管理页。

```text
素材库 128                     [导入 ▾] [整理]
[查找素材…]      状态 [全部 ▾]  [ ] 我审查的
▾ 2026-10 第一批   32 段 · 通过 20 · 待审查 8
  ▾ 样本A
    a-001.mp4  3000 帧  审查中 · 张三
    a-002.mp4  3000 帧  已通过 · 李四
  ▸ 样本B
▸ 张三 1102 标注包  12 段 · 通过 12
▸ 未分类  9 段
```

### 3. 批量导入

“导入”展开为：选择视频、选择文件夹、选择标注包（可多选）。

1. 筛选：视频按扩展名，`.zip` 当标注包，其余跳过（含 `.DS_Store`、`Thumbs.db`、`._*`）。
2. 一个小确认窗：视频几段、标注包几个、跳过几个、已存在几段；放到哪个文件夹（默认所选目录名）。
3. 后台一次传一个，显示进度。失败自动重试 2 次后跳过，继续下一个。素材库不锁，可以继续标注。
4. 完成后逐个文件说明结果，可重试失败项。

规则：

- **批量导入永远不覆盖。** 重复视频报告为“已存在”；覆盖重标只能从单个视频发起。
- 同名同大小的视频默认跳过，确认窗可改为“仍然上传”，服务器再用完整 SHA-256 判重。这也解决了中断的问题：关掉页面后重选同一文件夹，只传缺的。
- 标注包放进以包名命名的文件夹。
- 图片目前只存在本机，不进审查和导出，所以文件夹导入只收视频和标注包。

### 4. 谁在做什么

不做任务分配，不加按钮，全部从现有记录显示。这些状态只是提示，不影响审查和导出门槛，审查员仍可审查任何有内容的视频。

| 状态 | 怎么判断 | 旁边显示 |
| --- | --- | --- |
| 未开始 | 没保存过标注，也没有追踪结果 | |
| 标注中 | 保存过标注，还没有追踪结果 | 最后保存的人 |
| 待审查 | 有追踪结果，或从标注包导入，还没开始审查 | 最后保存的人 |
| 审查中 | 有未结束的审查轮次 | 最近确认的人 |
| 已通过 | 最近一次通过后内容没变 | 点“审查通过”的人 |
| 需重审 | 通过后内容变了 | 最后保存的人 |

追踪中继续叠加显示。分工靠文件夹和日常沟通，比如“第一批样本A归张三”。

打开素材库和切回页面时刷新列表，不用定时器。审查通过后加一个“下一段”按钮，跳到当前文件夹里下一段待审查的视频。

### 5. 批量导出

顶栏的“导出训练数据集”不再绑定当前视频，任何时候都能点。当前视频已通过时默认勾上。

```text
导出训练数据集
文件夹 [2026-10 第一批 ▾]  [x] 我审查通过的  [x] 只看未导出
[x] 全选 18 段                        共 54,000 帧
[x] a-001.mp4  审查:我  11-03
[x] a-002.mp4  审查:我  11-03
另有 2 段需重审，不能导出
                                [下一步：导出设置]
我的导出任务
  18 段  生成中 12,000 / 54,000 帧
  6 段   已完成 11-02   [下载] [删除]
  3 段   已失效：a-009.mp4 被改动   [删除]
```

1. 第一步选视频：默认筛出“我审查通过、还没导出的”。“我”指点击“审查通过”的账号（`passed_by`，已有数据，以前通过的也能筛出来）。
2. 前端逐段固定快照并显示进度，100 段预计一分钟内（未实测）。这一步页面要开着；失败的段列出原因，其余继续。
3. 第二步沿用现有导出设置（格式、划分、是否含原视频），服务器生成一个 ZIP，这时可以关页面。
4. 弹窗下方列出我的导出任务，可下载、删除；失效的任务写明是哪段被改了。

规则：

- **门槛不变**：每段都过 `require_passed`，只有审查通过且内容未再改动的才能进包。
- 一次最多 100 段（沿用）。更多时分批，`merge_training_exports.py` 可合并，划分按视频内容固定，分批不影响去向。
- “未导出”从现有导出记录现算：已完成的任务里有这一段，且导出时间晚于最近一次通过，就算已导出。

## 技术要点

| 改动 | 说明 |
| --- | --- |
| 新表 `media_folder(media_id, path)` | 没有记录的算“未分类”。删除视频时保留记录，从 `_trash/` 移回后路径还在 |
| `annotation_review_checks.frame_digest`（可空） | 确认时的帧内容摘要 |
| `/api/track/media` 增加路径、是否来自标注包、最后保存人 | 最后保存人复用 stamp 的缓存 |
| `/annotation-review/summary` 增加审查相关的人 | 只多查几列 |
| `/api/track/upload`、`/import-package` 增加可选的 `folderPath` | 旧调用不受影响 |
| 新接口 | `PUT /api/library/folder`（移动、重命名）；`GET /api/datasets/exports`、`DELETE …/{id}`（我的任务，含已导出记录） |

- **Chrome 93 / HTTP**：用 `webkitdirectory` 和 XHR 上传进度。`showDirectoryPicker` 在 HTTP 下不可用。
- **列表刷新**：写一个不重置当前视图的轻量刷新，不复用 `loadServerMedia`（它会重置视图）。
- **下载**：沿用视频播放的做法，用路径受限的 Cookie，令牌不进网址和日志。
- **减少冲突**：新界面写成独立组件和 store，`AnnotatePage.vue` 只改抽屉插槽。

## 实施顺序

| 阶段 | 内容 | 规模 | 做完后的变化 |
| --- | --- | --- | --- |
| 0 | 第 1 节 | 小 | 被改过的帧退回未确认；多段导出跑得动；大包能传能下；误删能找回 |
| 1a 文件夹 | 第 2、4 节 | 小到中 | 视频按文件夹分类，一眼看出谁在做什么 |
| 1b 批量导入 | 第 3 节 | 中 | 一次导入整个文件夹，失败不影响其他文件 |
| 1c 批量导出 | 第 5 节 | 中 | 筛出“我通过的、未导出的”，一次出一个 ZIP |

每个阶段的完成标准：

- 缺陷先补能在旧行为下失败的测试（探针已复现审查漏洞），正常流程和故障恢复成对验证。
- 按 TESTING 跑专项和完整浏览器回归。扩展现有的导入和导出用例，不新增套件。
- 阶段 0 和 1c 用隔离的合成数据跑一次多段导出，确认耗时不再随段数平方增长。
- 同步 WORKFLOW、API、STORAGE_LAYOUT、TESTING 和用户使用说明。

## 已确认

- 内部小团队自用，不做繁琐的功能。
- 团队共用一台服务器。
- 负责人、“分给我”、“标完了”先不做。
- 开放注册暂不改（按默认）。现在服务器所在内网的任何人都能注册并查看全部视频；如果这些视频不能让他们看到，加一个关闭注册的开关，只要几行代码。

## 暂不做

| 功能 | 现在不做的原因 | 什么时候再考虑 |
| --- | --- | --- |
| 负责人、分配、“分给我”、“标完了” | 人少，文件夹和日常沟通够用，状态也能自动判断 | 经常有人重复做同一段 |
| 管理员、角色、操作记录界面 | 团队互相信任，`_trash/` 能兜住误删，服务日志已记录删除的人 | 团队变大或有外部人员 |
| 改密码、重置密码 | 人少，忘了目前要手动改数据库，需要时写个小脚本 | 经常有人忘 |
| 在线状态 | 最后保存的人已能看出谁在做 | 经常同时改同一段 |
| 总览页、进度统计 | 文件夹行上的数字够回答“这批还差多少”，详细统计有现成的 ZIP | 需要经常看每人工作量 |
| 留言、修改回看、可分享链接 | 群里说就行 | 标注质量需要系统地反馈 |
| GPU 队列显示、取消追踪 | 人少，可以直接问 | 经常卡在排队 |
| 磁盘预检、ZIP 自动清理 | 服务器还剩约 2.8 TB，任务列表能手动删 ZIP | 磁盘紧张 |
| 拖入文件夹、断点上传、服务器收件箱 | 选择文件夹够用，内网失败重传单个文件即可 | 常传几百 GB |
| 交接包、更新回同一视频 | 共用一台服务器。批量导入标注包仍在 1b | 要和其他服务器来回交换数据 |

## 放弃的方案及原因

- **把视频目录物理移进文件夹**：`media_id`、历史记录和医院现有数据都依赖扁平目录，迁移和回滚风险大，换来的只是目录好看。
- **单独的文件夹表和管理页**：路径文字已能表达树，小团队不需要空文件夹和文件夹权限。
- **恢复领取、送审或给视频上锁**：这些流程已被删除，[0001](0001-多人协作工作区合并.md) 也明确不锁视频。
- **批量审查通过**：与逐帧人工检查的决定（[0003](0003-审查改为逐帧人工检查.md)）相反，浏览和勾选都不等于通过。
- **批量删除**：误操作的代价大，又不是常用操作。
- **服务器端批量任务表**：固定快照改完后很快，前端逐段调用现有接口就够，少一张表和一套恢复逻辑。代价是这一步页面要开着。
- **WebSocket 实时同步、多 worker**：与单进程部署冲突；打开素材库时刷新够用，保存时的版本检查负责正确性。
- **优化 `/annotation-review/summary`**：实测不是瓶颈。

## 影响

- **数据**：只新增一张表和一个可空列，媒体目录结构不变，只多一个 `_trash/`。预计不需要改离线升级 `contract`，实现时按 DOCKER_DEPLOYMENT 再核对一次；回滚规则不变。
- **部署**：nginx 配置随前端镜像更新；医院升级走完整离线包。
- **文档**：导航和导出门槛都不变，AGENTS 的关键边界不用改。
- **未验证**：100 段导出的实际耗时、真实视频规模、医院内网带宽。
