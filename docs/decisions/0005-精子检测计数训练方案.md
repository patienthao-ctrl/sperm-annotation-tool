# 0005 精子检测与计数的训练方案

- 日期：2026-11-05
- 状态：提议，待团队确认计数口径后改为“采用”

> 要点
> - 继续用 YOLO26s，从现有 `head-detector.pt` 微调，不换架构；整帧缩到长边 1024 训练和推理。
> - 正式训练前先统一框的大小、修标注、写明计数口径、改按场次和视野划分。
> - 每段视频抽几帧分别计数，取中位数作为这一段的结果，先不做跟踪去重。
> - 发布门槛看检测 F1、计数误差和最差批次，不再只看 mAP50-95。

## 背景

用户团队要训练检测并计数精子的模型，要求精准、高效。依据是审查通过的 185 段视频（5,156 帧，83,195 个头部框，全部单包单视频），以及现有检测器的全帧扫描和一轮本机试训练。业务明细不进仓库，这里只记汇总数字。

调查结论：

1. **框大小分成两群。** 10/26 批次编号 ≤125 的 93 段（占 45% 的框）框边长中位 51.6 px，其余 92 段 30.5 px（都换算到 4096 宽），两群之间没有过渡。头部暗核在所有批次都约 20 px，灰尘斑点也在同一位置，说明相机和放大倍率相同，这是标注差异。同心的松紧框 IoU 只有 0.35。决策 0002 里“框整体偏大是否来源于检测器”的问题，现在可以回答：不是，检测器给出的是紧框，松框来自这 93 段。这 93 段为什么不同尚未查明。
2. **标注的实际口径是“有头有尾”。** 检测器找到的持续目标里，已标注 2,434 个，未标注 931 个（平均每段 13 对 5）。已标注的 84% 能测到 40 px 以上的尾部脊线（按长边 2048 计），未标注的只有 20%，与是否游动无关。这是统计和目视抽查的推断，需要专家确认。
3. **真正的漏标不多。** 移动超过 5 个头距的目标只有 1.5% 未标注；带尾未标注对象约 150–190 个，相当于已标注量的 5–8%。
4. **帧间高度冗余，段内计数稳定。** 平均每个持续目标重复约 30 次；段内每帧计数的标准差平均 0.49。47% 的 objectId 只出现一帧（占框的 3.2%），不能直接去重计数。
5. **按视频划分有泄漏。** 核实到 13 对视频拍到同一视野（只比对首帧，是下限），其中 5 对跨越现有 train/val/test。64% 的帧来自 10/26 一天，所有批次来自同一光路。
6. **旧训练集的框定义不同。** `训练数据集-第一批/第二批` 框的是整条精子，现在框的是头，`merge_training_exports.py` 不会拦截。
7. **数据缺口。** 没有空帧，每帧 4–40 个目标，误报率在空视野上未测。视频为 MPEG-4，约 0.035 bpp、8–12 帧/秒。

本机试训练（Apple M4，从现有检测器微调 8 轮，训练 439 帧，在 46 段基准集的 241 帧上评估，框已统一，每组只跑一次）：

| 模型 | 输入长边 | F1（中心匹配） | 每段计数误差 | 秒/帧（M4） |
| --- | --- | --- | --- | --- |
| 现有检测器 | 1024 | 0.697 | 4.02 个（20.8%） | 0.037 |
| 现有检测器 | 2048 | 0.837 | 2.87 个（14.7%） | 0.134 |
| 微调，整帧训练 | 1024 | 0.936 | 1.24 个（6.4%） | 0.038 |
| 微调，768 裁块训练 | 2048 | 0.935 | 1.36 个（7.1%） | 0.135 |
| 微调，整帧训练，框未统一 | 1024 | 0.872 | 2.11 个（11.3%） | 0.032 |

由此得到五点判断：

- 统一框的作用已得到验证：其他条件相同，框不统一时 F1 从 0.936 降到 0.872，每段计数误差从 6.4% 升到 11.3%。
- 微调的收益主要来自学会排除无尾头状物：同样 0.93 的召回下，误检从 1,330 个降到 268 个。
- 分辨率目前不是瓶颈：1024 和 2048 的 F1 相同，速度差 3.5 倍，两者约 60% 的错误相同。画面明显过采样，缩到四分之一后头部附近的误差只有信号的约 8%。这推翻了起初“输入至少要 1536”的判断。
- 剩下的错误大多和标注有关：误检约 2/3 带尾巴证据，很可能是漏标；漏检中只有 33% 能测到尾巴（已标注对象总体是 84%）。
- 每段抽 3–5 帧取中位数就够：1 帧误差 7.8%，3 帧和 5 帧都是 6.5%，全部帧 6.4%。

## 决定

**阶段 0：数据口径。** 写标注准则 v1（专家确认）。构建训练集时把 93 段的框绕中心缩到 0.63 倍，审查通过的原始数据不动，换算写入 `model-record.json`。用训练集交叉微调两个模型，给每段视频生成误检和漏检清单（估计共 400–500 项），连同重复框走“标注 → 重新审查 → 重新导出”流程修正。按场次和视野分组固定基准集（46 段基准、25 段验证、114 段训练）。两人独立标注 30 帧，测人工上限。

**阶段 1：首轮训练。** 配置见下，先实测速度再定 batch 和轮数。

```bash
yolo detect train model=backend/app/model_assets/head-detector.pt data=<训练集>/data.yaml \
  imgsz=1024 batch=16 nbs=16 epochs=60 patience=15 \
  optimizer=AdamW lr0=0.0005 lrf=0.05 cos_lr=True warmup_epochs=1 close_mosaic=5 \
  mosaic=1.0 scale=0.2 translate=0.1 fliplr=0.5 flipud=0.5 \
  hsv_h=0 hsv_s=0 hsv_v=0.2 seed=2026
```

训练集每段抽 8 帧（10/26 批次先抽 5 帧）。最佳权重按验证集的 F1 和计数偏差选择，不用默认的 mAP50-95：静止目标相邻帧的框 IoU 有 8.9% 低于 0.75，高 IoU 段主要在反映标注抖动。

**阶段 2：受控对比。** 每次改一个变量，用验证集判断：输入分辨率（标注修正后复核 1024 / 1536 / 2048）、模型规模（n / s / n-P2）、每段帧数（3 / 8 / 全部）、翻转开关（图像明暗方向固定）、时序三通道、初始权重（现有检测器 / COCO）。

**阶段 3：计数层与泛化。** 在验证集上选阈值和每段帧数；7 个批次做留一场次交叉验证。试训练中完全留出的批次 F1 约 0.90–0.91，同批次留块约 0.93–0.95。

**阶段 4：上线与迭代。** 先在医院 GPU 上和人工结果并行比较。计数模型单独发布，暂不替换 `head-detector.pt`：工具用原图 512 切块调用检测器，尺度和训练时不同，试训练模型这样调用时在 4096 宽画面上召回只有 7%（现有检测器 99%）。要替换就必须先统一尺度并重新校准工具里的 0.15 / 0.5 / 0.7 阈值。新批次先当测试集记录前瞻指标，再并入训练。

**发布门槛（建议值，测出人工上限后调整）。**

| 指标 | 门槛 |
| --- | --- |
| 检测 F1（中心匹配） | 总体 ≥0.95，每批次 ≥0.90 |
| 每段计数误差 | 平均绝对百分比 ≤5% |
| 每段计数偏差 | 绝对值 ≤0.3 个 |
| 每段计数 95% 一致性界限 | ±3 个以内 |
| 最差批次的每段误差 | ≤2 个 |
| 空视野误报 | 平均每帧 ≤0.1 个（当前无数据，未测） |
| 回归保护 | 任何批次的 F1 相对上一版下降不超过 0.01 |

现有 `detector_train_eval.py` 需要相应调整：用全部帧；颜色增强是默认值；`verdict()` 只看 mAP50-95 和召回；没有计数指标和按批次报告；验证集仍按哈希划分。默认的 `imgsz=1024` 可以保留。

## 放弃的方案及原因

- **密度图回归计数：** 目标稀疏，最近邻距离中位约 10 个头距，只有 1.2% 的框与邻居重叠。检测已够用，结果还能逐个复核。
- **用原图 512 切块做计数推理：** 4096 宽的帧要切 63 块，比全帧长边 2048 慢约 5 倍，现有检测器上 F1 还略低（0.78 对 0.80，100 帧抽样）。
- **高分辨率裁块训练：** 试训练已对比，F1 没有提高，训练时间约 1.6 倍，推理慢 3.5 倍。标注修正后再复核一次。
- **把全部帧放进训练：** 帧间冗余约 30 倍。是否值得由阶段 2 确认。
- **现在就用跟踪去重计数：** 短片段内每帧计数已很稳定，ID 又不可靠。做活力分析时再按位置重新连接。
- **现在就换架构或加二阶段分类器：** 当前最大的问题在标注口径和输入设置。只有阶段 1–2 后仍以无尾误检为主，才考虑用原图裁块判断有无尾巴。
- **直接修改 ZIP 里的标签：** 会绕过审查和溯源。

## 影响

- 代码：新增训练集构建脚本（选帧、统一框、分组划分）；`detector_train_eval.py` 增加计数指标和按批次报告；`merge_training_exports.py` 增加框大小校验。实现时再更新 WORKFLOW 和 PROJECT_STRUCTURE。
- 数据：训练只用审查结果里的包，不混入旧训练集。`head-detector.pt` 在通过门槛前不替换，用途仍为非商业（见 0002）。
- 工具：查明松框的原因，避免新数据重复。分析期间根目录新出现的 264 段合并包中，10/26 编号 ≤125 的 125 段同样偏松，统一时要一并处理。如果专家决定无尾头也要计数，现有标注要补标，方案需重新评估。
- 未执行：GPU 服务器上的训练与验收、留一场次交叉验证、人工上限测试；时序三通道和翻转开关没有试。文中结果都不代表临床性能。
